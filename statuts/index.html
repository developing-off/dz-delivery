Statuts de colis, modèles et erreurs

Chaque transporteur algérien a ses propres statuts : libellés français chez Yalidine, codes numériques chez Maystro, états propres à ZRExpress, Ecotrack ou NoEST. dz-delivery les ramène à sept statuts unifiés, avec les mêmes modèles et les mêmes codes d’erreur en TypeScript et en PHP.

Convertir un statut natif (webhooks, imports)

Les mappers sont exportés : utilisez-les quand vous recevez un statut natif en dehors de track(), par exemple dans un webhook Maystro.

TypeScript
import { mapYalidineStatus, mapMaystroStatus, PARCEL_STATUSES } from '@dz-delivery/core';

mapYalidineStatus('Sorti en livraison');  // 'in_transit'
mapMaystroStatus(41);                     // 'delivered' (code ou nom)
PARCEL_STATUSES;                          // les 7 statuts, dans l'ordre
// Aussi : mapZRExpressStatus, mapEcotrackStatus, mapNoestStatus, mapEcomStatus, mapMdmStatus, mapElogistiaStatus
PHP
use DzDelivery\Support\StatusMapper;
use DzDelivery\Models\ParcelStatus;

StatusMapper::map('yalidine', 'Sorti en livraison');  // 'in_transit'
StatusMapper::maystro(41);                             // 'delivered' (code ou nom)
ParcelStatus::DELIVERED;                               // constantes, ParcelStatus::ALL pour la liste

Codes d’erreur

Toute erreur est levée sous forme de ShippingError (champs détaillés dans Modèles). Le champ code vaut l’une de ces valeurs :

codeQuand
AUTH_FAILED401 / 403, identifiants manquants ou invalides.
VALIDATION_ERROR400 / 422, ou échec de la validation côté SDK (avant tout appel HTTP).
NOT_FOUND404, colis ou localité introuvable, ou échec de la résolution d’un nom (wilayaName, communeName).
RATE_LIMITED429.
NOT_SUPPORTEDLe transporteur ne propose pas cette opération (par exemple l’annulation).
PROVIDER_ERROR5xx, ou réponse inattendue / illisible du transporteur.
NETWORK_ERRORTimeout, DNS, connexion refusée.
UNKNOWNTout le reste.

Correspondance HTTP → code par défaut : 400, 422 → VALIDATION_ERROR, 401, 403 → AUTH_FAILED, 404 → NOT_FOUND, 429 → RATE_LIMITED, 5xx → PROVIDER_ERROR, autres 4xx → UNKNOWN.

Exemples de gestion (relance sur RATE_LIMITED, affichage des erreurs de validation) : guide PHP.

Conventions

SujetRègle
NommagecamelCase pour les champs et les méthodes, en TS comme en PHP (les objets PHP exposent des propriétés publiques readonly aux mêmes noms).
IdentifiantsTous les ids renvoyés par le SDK sont des chaînes (les transporteurs utilisent des UUID, des entiers ou des codes). Les entrées acceptent string | int.
MontantsEn DZD, sous forme de nombres (dinars, pas centimes). currency vaut toujours "DZD".
Poids / dimensionsPoids en kg, dimensions en cm.
DatesChaînes ISO 8601 avec fuseau horaire (par exemple 2025-12-23T15:23:54+00:00), en TS comme en PHP.
TéléphonesChaînes. Chaque provider normalise au format du transporteur (par exemple 0550123456 ↔ +213550123456).
Optionnel? = optionnel. Une valeur optionnelle absente vaut undefined (TS) / null (PHP).
AsynchroneLes méthodes TS renvoient Promise<T>. Les méthodes PHP sont synchrones et renvoient T.
ErreursTous les échecs sont levés en ShippingError (voir Codes d’erreur). Jamais de null / false pour signaler une erreur.

Le champ raw

Chaque modèle renvoyé (Parcel, TrackingEvent, FeeQuote, Location, ShippingError) peut porter un champ optionnel raw contenant la réponse native non modifiée de l’API (ou le fragment utile).

  • raw sert au débogage et aux usages avancés. Sa forme ne fait pas partie du contrat et peut changer quand le transporteur modifie son API.
  • Votre code applicatif ne devrait pas en dépendre pour sa logique principale.
  • raw est rempli par défaut ; l’option client includeRaw: false le désactive.

TypeScript
export type ParcelStatus =
  | 'pending' | 'created' | 'in_transit' | 'delivered'
  | 'returned' | 'cancelled' | 'unknown';

export interface HealthCheckResult {
  ok: true;
  provider: string;
  /** Durée aller-retour en millisecondes. */
  latencyMs: number;
}

export interface ShippingProvider {
  readonly name: string; // 'zrexpress' | 'yalidine' | ...
  createParcel(input: ParcelInput): Promise<Parcel>;
  track(trackingNumber: string): Promise<TrackResult>;
  getFees(query: FeeQuery): Promise<FeeQuote>;
  getWilayas(): Promise<Location[]>;
  getCommunes(wilayaId: string | number): Promise<Location[]>;
  getStopDesks(query: StopDeskQuery): Promise<StopDesk[]>;
  listParcels(query?: ParcelListQuery): Promise<ParcelListPage>;
  cancelParcel(trackingNumberOrId: string): Promise<void>;
  healthCheck(): Promise<HealthCheckResult>;
}
PHP
namespace DzDelivery\Contracts;

use DzDelivery\Models\FeeQuery;
use DzDelivery\Models\FeeQuote;
use DzDelivery\Models\HealthCheckResult;
use DzDelivery\Models\Location;
use DzDelivery\Models\Parcel;
use DzDelivery\Models\ParcelInput;
use DzDelivery\Models\ParcelListPage;
use DzDelivery\Models\ParcelListQuery;
use DzDelivery\Models\StopDesk;
use DzDelivery\Models\StopDeskQuery;
use DzDelivery\Models\TrackResult;

interface ShippingProviderInterface
{
    public function getName(): string;
    public function createParcel(ParcelInput|array $input): Parcel;
    public function track(string $trackingNumber): TrackResult;
    public function getFees(FeeQuery|array $query): FeeQuote;
    /** @return Location[] */
    public function getWilayas(): array;
    /** @return Location[] */
    public function getCommunes(string|int $wilayaId): array;
    /** @return StopDesk[] */
    public function getStopDesks(StopDeskQuery|array $query): array;
    public function listParcels(ParcelListQuery|array|null $query = null): ParcelListPage;
    public function cancelParcel(string $trackingNumberOrId): void;
    public function healthCheck(): HealthCheckResult;
}

Comportement des méthodes

  • createParcel : valide les champs requis côté client (VALIDATION_ERROR avant tout appel HTTP) et résout wilayaName / communeName / codes de wilaya en ids du transporteur. Si le transporteur ne renvoie qu’un id à la création, le provider peut relire le colis pour remplir trackingNumber et status.
  • track : renvoie le Parcel actuel et son historique. Si le transporteur a besoin d’un id interne pour l’historique, le provider le retrouve à partir du numéro de suivi.
  • getFees : renvoie un seul tarif pour la destination et le mode demandés. NOT_FOUND si la destination n’a pas de tarif.
  • getWilayas / getCommunes : ne renvoient que les localités livrables quand le transporteur fournit l’information. Les résultats peuvent être mis en cache en mémoire pendant la vie du client.
  • cancelParcel : accepte un numéro de suivi ou un id interne. NOT_SUPPORTED si le transporteur ne permet pas l’annulation, VALIDATION_ERROR / PROVIDER_ERROR si le colis n’est plus annulable. Renvoie void car certains transporteurs répondent 204 No Content : appelez track() ensuite pour connaître le nouveau statut.
  • getStopDesks : liste les stop desks / points relais d’une wilaya (éventuellement d’une commune). VALIDATION_ERROR si le transporteur exige communeId et qu’il manque, NOT_SUPPORTED sans liste disponible. Peut lever NOT_FOUND avec une indication dans details quand le filtre commune ne donne rien alors que la wilaya a des bureaux (cas typique des hubs ZRExpress).
  • listParcels : liste paginée des colis du compte avec leur status unifié, sans l’historique (utilisez track()). NOT_SUPPORTED si le transporteur n’expose pas de liste. Préférez les webhooks à un polling agressif quand ils existent.
  • healthCheck : vérifie identifiants et connectivité avec une requête authentifiée légère (liste des wilayas). Appelle toujours le réseau (ignore le cache). Renvoie { ok: true, provider, latencyMs }, sinon lève une ShippingError (AUTH_FAILED, NETWORK_ERROR, RATE_LIMITED…). Ne lève jamais NOT_SUPPORTED.

Hors du contrat unifié

Volontairement absents de l’interface commune : endpoints de catalogue (produits, catégories, stock), modification de colis (adresse, montant, produits), échanges, remboursements, sacs d’enlèvement, réclamations, clients, trésorerie et paiements, rapports, gestion des endpoints webhook. Ils pourront arriver plus tard sous forme de modules propres à un transporteur, sans changer ShippingProvider.

Les fonctions plus riches d’un transporteur sont exposées comme extras sur sa classe concrète, par exemple pour ZRExpress la création / suppression en masse, les étiquettes et la vérification des webhooks (page ZRExpress, ZREXPRESS.md).

Ce contrat est versionné (v0.1) : tout changement cassant des modèles ou de l’interface implique une nouvelle version et une publication des deux paquets.
